MetaProof

by Lanchenba Mutum
Evidence-based authenticity analysis for images

MetaProof checks an image's metadata, its file structure, its signed C2PA Content Credentials, invisible generator watermarks and its pixels, then combines the evidence into one explainable verdict: likely authentic, edited, likely AI-generated or inconclusive. Every verdict shows the evidence behind it, and the system says "inconclusive" rather than guess.

01

Summary and key numbers

MetaProof is a full-stack web application, built from an empty repository, that answers one question about an uploaded image: what does the evidence say about where it came from? It is live, free to use, needs no account and deletes every uploaded file after analysis.

36,528Training images for the shipped detector (v3), from 30 generators and 6 real-photo sources

What was built

  • A web app (React, TypeScript) with upload, live analysis progress, an explained report, a shareable report link, history kept on the user's device, a method page and a status page. It installs on phones and appears in Android's share menu.
  • An API (Python, FastAPI) that validates uploads safely, queues analysis jobs in PostgreSQL and runs five analyzers in a background worker.
  • An AI-image detector trained by the author: frozen CLIP ViT-B/16 features with a small trained classifier, calibrated, and compressed to 121 MB so it fits a 512 MB free server.
  • An evidence engine that weighs every finding and picks a verdict only when the evidence is strong enough and clearly points one way.
  • A "seen before" search that finds resized or recompressed copies of an image using vector similarity (pgvector).
  • An evaluation suite: detector metrics on unseen generators, robustness to everyday edits, a C2PA tamper benchmark and pipeline timings.
  • Production operations: CI on every push, automatic deploys, a separate development database, uptime monitoring and data retention.

The guiding principle

Wrongly calling a real photo fake is the costlier mistake. So missing data is never held against a file, the detector's score only decides a verdict on its own when it is very high, signed proof (C2PA) outranks statistical guesses, and when the evidence is weak the answer is inconclusive.

02

The problem, and what MetaProof does about it

The problem

Images are easy to edit, recompress, re-upload and generate with AI. Checking them by eye is slow and unreliable. Pure AI detectors give a bare percentage, are often wrong on new generators and real photos, and do not explain themselves. A useful tool must gather several kinds of evidence, weigh them honestly and show its working.

The approach: several independent kinds of evidence

EvidenceWhat it can showWhat it cannot show
Metadata (EXIF, XMP, PNG text)Camera make and model, editing software, AI-generator tags (e.g. a Stable Diffusion prompt in a PNG chunk)Metadata is easy to strip or forge, so it is weighed lightly
File structureHow the file was written: JPEG quality tables, segments, colour profile, data appended after the imageExplains the file only; every finding is neutral
C2PA Content CredentialsA cryptographically signed history: who created or edited it, with what tool, and whether it changed since signingMost images have none, and re-saving removes them; absence proves nothing
Invisible watermarkThe hidden mark Stable Diffusion 1.x/2.x and SDXL embed in their outputThe mark usually does not survive resizing; absence proves nothing
AI-image detectorA calibrated probability that the pixels came from a generatorA probability, not proof; weaker on the newest generators

The four verdicts

VerdictTypical evidence
Likely authenticConsistent camera metadata plus the structure of an untouched camera file, and no signs of AI. Requires more support than the other labels, because camera EXIF is easy to forge.
EditedEditing software in the metadata, or signed C2PA edit actions.
Likely AI-generatedA signed C2PA "AI-generated" claim (decides on its own), a generator watermark, generator metadata, or a very high detector score.
InconclusiveNot enough evidence, or evidence pointing different ways. This is the most common honest answer, because most images carry no provenance data.

The 20 October production incident (a useful case study)

The live API stopped answering. The investigation found three separate faults:

  1. Root cause: a database migration (0004) had been applied to the production database from a laptop, but the deployed code was 8 days old and did not know that migration. On every start the container ran alembic upgrade head, which failed on the unknown revision, so the server never started and requests hung.
  2. Why the new code never deployed: Render's GitHub app had lost access to the repository, so pushes no longer triggered deploys.
  3. Why the keep-warm check kept failing: GitHub runs scheduled workflows hours late under load, and a single 120-second attempt could not outlast a cold start.

Fixes: a manual deploy of the latest code; repository access restored for Render; the client now retries through cold starts (with a regression test); the worker no longer blocks startup on the database; database connections time out after 15 s; a separate dev database branch for local work; and UptimeRobot replaced the unreliable GitHub schedule. The lesson, in one line: never run migrations from a laptop against production.

04

System architecture

The life of one upload

  1. Upload. The browser posts the file (with a neutral name, upload; the real filename stays on the device). The API streams it to a private temp file, computing SHA-256 on the way, checks the real type from the file's bytes (not its extension), and decodes it once under a 25 MB size limit and a 30-megapixel limit, which also blocks decompression bombs.
  2. Deduplicate. If the same file (same hash) was analyzed before under the current pipeline, the existing job is returned at once.
  3. Queue. A job row is inserted in PostgreSQL and the worker is woken. The worker claims jobs with SELECT … FOR UPDATE SKIP LOCKED, so several workers could share the queue safely without Redis. It sleeps instead of polling, so the serverless database can scale to zero.
  4. Analyze. The five analyzers run in turn; each writes its findings, raw output and duration. Progress (current_step) is published so the page can tick off steps. One failing analyzer cannot sink the report.
  5. Decide. The evidence engine weighs all findings into a verdict with its top reasons.
  6. Clean up. The original file is deleted whatever the outcome. A hash, a small WebP thumbnail, the findings and the CLIP embedding are kept for 90 days.
  7. Read. The page polls the job until it is done, then shows the report. The report is shareable at /report/<sha256>.

Key design decisions

05

The five analyzers and the evidence engine

Every analyzer turns the file into typed findings. A finding has a signal (authentic, edited, AI or neutral), a strength (weak, moderate, strong or conclusive) and a plain-language message. Raw output is stored too, so the report can show details.

5.1 Metadata analyzer

Reads EXIF, XMP and PNG text chunks with Pillow; adds ExifTool's full tag dump when the binary is present (it is in the Docker image). Signals include camera make and model, editing software, generator names and prompts written by AI tools, and timestamps. GPS coordinates are never stored. Because metadata is easy to forge or strip, camera EXIF alone cannot make a file "likely authentic".

5.2 File-structure analyzer

Lists JPEG segments and PNG, WebP and HEIF chunks, reads JPEG quantization tables and estimates the quality the file was saved at, names the ICC colour profile and measures data appended after the image. It explains how the file was written (for example, "saved by an editor at quality 85" or "camera-original structure"); every finding is neutral on its own, but it supports the authentic verdict. Includes HEIC/HEIF support (iPhone photos).

5.3 C2PA analyzer

Reads and validates Content Credentials with the official c2pa-python SDK. It reports whether a manifest is present, whether it validates, who signed it, the recorded actions (created, edited, converted), any AI-generation source type (trainedAlgorithmicMedia), and the history of ingredients. A valid AI-generation claim is conclusive. A missing manifest is neutral. A manifest proves who signed and that the file has not changed since; it does not prove the scene is real.

5.4 Invisible-watermark analyzer

Stable Diffusion 1.x/2.x and SDXL hide a fixed message in their output using the DWT-DCT method of the invisible-watermark library. MetaProof reimplements that decoder in numpy (the original needs PyTorch) and checks it bit for bit against the library in tests. Finding the mark is strong evidence; not finding it says nothing, because resizing or heavy recompression removes it.

5.5 AI-image detector

A frozen CLIP ViT-B/16 image encoder plus a small trained head that outputs a calibrated probability, served with ONNX Runtime. Before scoring, added borders (meme caption bands, phone screenshot app bars) are trimmed. It also outputs the 512-dimensional embedding used for the "seen before" search. Chapter 6 covers it in depth.

5.6 Error Level Analysis view (ELA)

The report includes an ELA view computed in the browser: the image is re-saved as JPEG and the difference is amplified, which can make regions with a different compression history stand out. It is shown as a visual aid for the reader, not counted as evidence, because ELA is easy to misread.

5.7 The evidence engine (backend/app/engine.py, version 0.2.0-rules)

StrengthWeight
weak0.5
moderate1.0
strong2.0
conclusive10.0 (decides alone)
  1. Weights are summed per outcome (authentic, edited, AI). Neutral findings count for nothing.
  2. A conclusive finding (such as a valid signed C2PA AI claim) decides the verdict on its own.
  3. Otherwise a label needs at least 1.0 total support and a lead of at least 0.75 over the runner-up.
  4. "Likely authentic" needs at least 2.0, because camera EXIF is easy to forge.
  5. If none of this holds, the verdict is inconclusive. The report always lists the top reasons and says what decided the verdict.

5.8 How detector scores become evidence

Detector scoreBecomesEffect
≥ 0.91strong AI evidenceCan decide a verdict alone. 70% of unseen-generator AI images and 1.3% of real images score this high.
0.79 – 0.91weak AI evidenceCounts only together with other evidence.
0.05 – 0.79neutral ("unsure")No effect on the verdict.
< 0.05weak support for a real photoA small push towards authentic.

The thresholds were chosen on a held-out calibration split so that detector v3 flags no more real images than v1 did at its 0.95 threshold.

06

The AI-image detector: data, training and results

6.1 Design

  • Frozen foundation-model features (the UnivFD idea): OpenAI CLIP ViT-B/16 turns each image into a 512-number embedding. Only a small multilayer perceptron (MLP) head, about 130,000 parameters, is trained on top. Frozen features generalize to new generators far better than a network trained from scratch.
  • Split by generator, not by image. The test set contains only generators the model never saw, so the score measures generalization, not memorization.
  • Standardize every image: shorter side to 256 px and a JPEG round trip at quality 90, then CLIP's resize, crop and normalization. In the raw data, real photos are mostly small JPEGs and AI images large PNGs; without this step a model learns "PNG means AI". The API applies the identical step, verified bit-identical to training.
  • Calibration by temperature scaling (T = 1.176 for v3) on a held-out split, so 0.8 means roughly 80%. That lets the evidence engine use fixed, interpretable thresholds.
  • Trained on a laptop: an NVIDIA RTX 4050 laptop GPU (6 GB). Images were streamed from Hugging Face and decoded in memory; only CLIP features were kept on disk (42 MB for 33,000 images).

6.6 Real camera photos

Test sets of web images say little about what users upload most: originals straight from a phone or camera. On 1,304 camera originals from 97 devices (2012–2026 phones, mirrorless and DSLR cameras) the live model flags 0.5% at the strong threshold (95% upper bound 1.1%), and 0.5% of their social-media copies. The thresholds hold on real camera files.

In plain words: on AI generators it has never seen, the detector separates AI images from real ones with an AUC of 0.97. When it is confident enough to decide a verdict, it is right 99% of the time and flags only about 1 in 200 real camera photos. It does this with a 121 MB model that runs in about half a second on one ordinary CPU core, needs no GPU and costs nothing to host.

Where it is weaker: the newest photorealistic generators (GPT Image 2, Nano Banana 2, Qwen Image 2.1, FLUX.2) reach an AUC of only 0.770, and corner crops or heavy edits lower detection. Chapter 6 and the limitations chapter give the details. These numbers are from the project's own test sets; the detector has not been benchmarked head-to-head against commercial tools.

Cost check for v5/v6: on Render's free CPU, v3 takes about 5 s per image; a full-resolution model would take about 14 s. Speed was a second reason to keep v3.

At 30,000 analyses the HNSW index is about 80× faster than an exact scan while returning the same best match in every query. A lesson recorded during benchmarking: random vectors gave only 39–68% recall, because random vectors have no neighbourhood structure; real CLIP embeddings cluster, which is what HNSW exploits.

Storage and retention

About 6 KB per analysis for the row and embedding, plus ~7 KB thumbnail and a few KB of findings, so Neon's 0.5 GB free tier holds roughly 25,000–30,000 analyses. Images not analyzed for 90 days are deleted with everything derived from them. The API logs a warning at 400 MB. The database used 9.1 MB on 20 October 2026.

Two database branches

main is production (used by Render). dev is a copy-on-write branch for local development, so migrations and experiments can never break the live site again.

Advantages, in plain words

  1. Several kinds of evidence, one honest answer. Signed proof outranks statistics, missing data is never held against a file, and weak evidence gives "inconclusive" instead of a guess.
  2. Explains itself. Every verdict names what decided it, in words a non-expert can follow.
  3. Measured honestly. Accuracy is reported on generators the model never saw, under recompression and edits, on real camera photos, and its weak spots are published.
  4. Conservative by design. At the strong threshold it is right 99% of the time when it says AI on unseen generators, and flags about 0.5% of real camera originals.
  5. Private. No account, no stored originals, filename never sent.
  6. Open and cheap. MIT-licensed code that runs entirely on free tiers.

Limitations

Read this chapter before relying on a verdict or publishing claims about the system.

Detection

  • The newest photorealistic generators are mostly missed. GPT Image 2, Nano Banana 2 and Qwen Image 2.1 reach only 21–24% at a score of 0.5 and 5–8% at the strong threshold. The cause is in the features (256 px CLIP view), not the amount of training data.
  • A detector score is a probability, not proof; about 9% of real web images score above 0.5, which is why only scores ≥ 0.91 can decide a verdict.
  • Corner crops and screenshots lower detection (to about 41–57% at the strong band).
  • Heavily filtered or edited real photos can be flagged.
  • Does not localize edits: splicing, inpainting or object removal inside a real photo are not detected.

Provenance and metadata

  • Most images carry no C2PA credentials, and normal re-saving removes them; "inconclusive" is therefore the most common verdict.
  • Metadata can be stripped or forged, so it is weighed lightly.
  • Watermark detection covers only Stable Diffusion 1.x/2.x and SDXL marks, which do not survive resizing.

Product and operations

  • Images only. Video analysis from the proposal is not built.
  • Free hosting: about 9 s per analysis, a cold start of about a minute if the server sleeps, 20 uploads per hour per IP, 500 per day overall, and roughly 25,000–30,000 stored analyses.
  • One server instance: no horizontal scaling or redundancy.
  • No user accounts: history is per browser and is lost if browser data is cleared.
  • The detector weights are licensed non-commercial only (CC BY-NC-SA 4.0), because of the training data.
  • Evaluation sets are a few hundred images per generator, so differences of a few points can be noise.

Future work

  1. A full-resolution detector that keeps camera photos safe: a few thousand more unedited camera originals as real examples, full-size outputs of the newest generators, and a larger test set so small gains can be told from noise.
  2. Video: FFprobe metadata, C2PA for video, and frame sampling through the existing image pipeline.
  3. Local edit detection: splicing and inpainting localization, shown as a heat map.
  4. More watermark families as generators publish decoders (for example, invisible marks from other open models).
  5. A learned evidence engine fitted on a labelled validation set, replacing hand-set weights.
  6. Paid hosting (or a self-hosted server) to remove cold starts and speed analysis to about 1–2 s.
  7. CI-gated deploys: switch Render to "After CI checks pass" so a failing test blocks a deploy.

Glossary for study

TermMeaning
AUC (ROC-AUC)The probability that a random AI image scores higher than a random real image. 0.5 is chance; 1.0 is perfect.
Precision / recall / F1Precision: of the images flagged as AI, the share that really are. Recall: of the AI images, the share flagged. F1: their harmonic mean.
Calibration, temperature scalingAdjusting a model so its scores mean what they say (0.8 ≈ 80%). Temperature scaling divides the model's raw output by one fitted number.
CLIP, ViT-B/16OpenAI's image-text model. ViT-B/16 is a Vision Transformer that splits an image into 16×16-pixel patches.
Frozen features, linear probe, MLP headUsing a pre-trained network unchanged as a feature extractor and training only a small classifier on top.
Held-out / unseen generatorsGenerators kept entirely out of training, to measure generalization.
Quantization (8-bit weight-only)Storing model weights in 8 bits to save memory while still computing in 32-bit floats.
ONNX, ONNX RuntimeA portable model format and a fast engine to run it without PyTorch.
C2PA, Content Credentials, manifestAn open standard for signed provenance records attached to media; the manifest holds signed claims and assertions.
EXIF, XMP, ICCCamera metadata, Adobe's extensible metadata, and colour-profile data inside image files.
JPEG quantization tableThe table that controls JPEG compression; it reveals the quality setting and often the software that saved the file.
DWT-DCT watermarkA hidden mark embedded in an image's frequency domain (wavelet then cosine transform).
ELA (Error Level Analysis)Re-saving a JPEG and amplifying the difference to reveal regions with a different compression history.
SHA-256A cryptographic hash; identical files give identical hashes.
pgvector, HNSWA Postgres extension for vectors; HNSW is a graph index for fast approximate nearest-neighbour search.
FOR UPDATE SKIP LOCKEDA Postgres row-locking clause that lets several workers take different jobs from one table without conflicts.
Migration (Alembic)A versioned script that changes the database schema.
Cold startThe delay when a sleeping free server is woken by a request.
PWA, service worker, share targetA web app that installs like a native app; a background script; registration in the phone's share menu.
CI / CDContinuous integration (tests on every change) and continuous deployment (automatic release).
Decompression bombA small file that expands to an enormous image to exhaust memory.
Clopper-Pearson intervalAn exact confidence interval for a proportion, used for small false-alarm rates.
